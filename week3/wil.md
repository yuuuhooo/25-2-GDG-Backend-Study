## Repository 계층
**Repository**: 데이터베이스에 접근하여 CRUD 작업을 수행하는 계층
- Create: 데이터 생성
- Read: 데이터 조회
- Update: 기존 데이터 수정
- Delete: 데이터 삭제

## ORM과 JPA

**데이터베이스에 접근하려면?**
- 애플리케이션 서버는 DB가 이해할 수 있는 SQL을 연결된 커넥션을 통해 DB에 전달
- DB는 전달된 SQL을 수행하고 그 결과를 응답, 애플리케이션 서버는 결과 활용.

### JDBC
- java에서 database에 접근하기 위한 표준화된 API
- 데이터베이스에 종속되지 않고 같은 방식으로 코드를 작성할 수 있음
- 내부적으로는 이 JDBC가 각 데이터베이스에 맞는 드라이버를 통해 실제 SQL을 전달해줌.

_그러나 SQL을 직접 다루는 방식은_

- 반복적인 SQL 코드 작성(객체의 필드가 하나만 달라져도 관련된 SQL문 일일이 수정해야 함)
- SQL에 의존적인 개발(비즈니스 모델보다 SQL문 관리에 더 큰 비용 들어감)
- 객체-데이터베이스 간 패러다임 불일치(자바는 객체 지향, 그러나 RDB는 객체 지향이라는 개념 없음. 지향하는 목적이 달라 기능이나 표현 방식이 다름) => 직접 매핑하려고 하면 매핑 코드가 매우 복잡해짐.


### ORM
- Object-Realational Mapping
- 객체와 관계형 데이터베이스의 데이터를 자동으로 매핑(연결)해주는 것
- 객체-데이터베이스 간 패러다임 차이 해결(객체 지향적인 애플리케이션 구현에만 집중할 수 있게 됨)
- 반복적인 CRUD SQL 자동으로 처리(개발 생산성 향상)

### JPA
- Java Persistence API
- 자바 진영의 ORM 기술 표준
- 자바에서 객체를 데이터베이스에 저장하고 관리하기 위한 인터페이스와 기능을 제공하는 API
- 대표적인 JPA 구현체는 Hibernate

JPA는 자바 애플리케이션과 JDBC 사이에서 동작함. 개발자가 직접 JDBC를 다루지 않아도 JPA가 내부적으로 JDBC를 사용해서 데이터베이스와 통신함.



**_요약_**

- 개발자가 어떤 객체를 데이터베이스에 저장을 할 때 INSERT SQL을 직접 작성하는 게 아니라 마치 자바 컬렉션의 객체를 저장하듯이 JPA에게 객체를 전달하기만 해도 이 JPA가 적절한 INSERT SQL을 자동으로 생성해서 데이터베이스에 객체를 저장해주는 것.



## JPA의 동작 방식

### Entity Manager
- 엔티티 객체를 데이터베이스와 연결해주는 창구 역할
- 엔티티 매니저를 사용해서 SQL을 직접 작성하지 않고도 CRUD 할 수 있음
  - 등록-> em.persist()
  - 조회-> em.find()
  - 삭제-> em.remove()  
- 엔티티 매니저는 엔티티를 영속성 컨텍스트에 저장

_엔티티: 데이터베이스에 저장할 객체, 테이블과 1대1 매핑되는 객체_


### 영속성 컨텍스트
- JPA에서 엔티티를 관리하기 위해서 만들어져 있는 가상 공간
- 애플리케이션과 데이터베이스 사이에서 객체를 보관하는 가상의 데이터베이스 같은 역할이고, 엔티티 매니저를 통해 영속성 컨텍스트에 접근할 수 있음
- 엔티티는 영속성 컨텍스트에 의해 생명 주기가 관리됨

#### 엔티티 생명 주기
- 비영속: 영속성 컨텍스트와 관련 없는 상태
- 영속: 영속성 컨텍스트에 저장된 상태. 엔티티가 영속성 컨텍스트에 의해 관리됨.
- 준영속: 영속성 컨텍스트에 저장되었다가 분리된 상태.
- 삭제: 영속성 컨텍스트에 엔티티가 삭제 대상으로 등록된 상태.


#### 영속성 컨텍스트의 특징
- 1차 캐시
- 동일성 보장
- 트랜잭션을 지원하는 쓰기 지연
- 변경 감지


**트랜잭션**
- 데이터베이스에서 수행되는 작업의 단위
- 여러개의 데이터베이스 연산을 하나의 논리적인 작업 단위로 묶어서 실행
  - 모든 연산이 성공적으로 수행되면 트랜잭션을 커밋하여 데이터베이스에 반영
  - 하나라도 실패하면 롤백하여 이전 상태로 되돌림
- 더 이상 쪼개질 수 없는 원자성을 가짐

_ex. 사용자가 상품을 결제 할 때_

- 주문 정보 저장 -> 상품 재고 차감 -> 회원 포인트 적립 -> 커밋(데이터베이스 반영)

- _그러나 만약 상품 재고 차감 과정에서 에러가 발생한다면 주문 정보 저장 이전으로 롤백 !!_


#### 엔티티 등록 예시
**1. 멤버 1번을 새로 등록하기 위해 멤버 엔티티 하나 생성 em.persist(member1)**
  - 이 시점에서 멤버 1은 단순히 자바 객체 1일 뿐임. 아직 JPA와 아무런 관련 없음. 
  - 즉 영속성 컨텍스트와 연결되지 않은 비영속 상태
  - em=엔티티매니저 / .persist()=DB에 insert하는 명령이 아니라 영속성 컨텍스트에 등록하는 명령. 이제부터 JPA에 관리하는 영속 상태가 되는 것.
  - 영속성 컨텍스트에 저장 => 이 시점에서 JPA는 내부적으로 엔티티를 DB에 저장하기 위한 SQL을 만들고 이를 영속성 컨텍스트에 보관함.

**2. 멤버 2번을 등록하기 위해 멤버 엔티티 하나 생성 em.persist(member2)**

**3. 등록하는 과정의 트랜잭션이 커밋**

  - JPA가 내부적으로 em.flush()를 자동으로 실행
  - 영속성 컨텍스트의 변경 내용을 데이터베이스에 동기화
  - 쿼리를 모아뒀다가 한 번에 실행

#### 트랜잭션을 지원하는 쓰기 지연
- 데이터베이스에 바로 쓰는 것이 아니라 변경 사항들을 모아두었다가 트랜잭션이 완료되는 시점(커밋)에 한 번에 묶어서 DB에 보내는 구조
- 쿼리를 데이터베이스에 한 번에 전달할 수 있으므로 데이터베이스와의 네트워크 통신 횟수를 줄여 성능을 최적화 할 수 있음


#### 엔티티 조회 예시
**1. 멤버 엔티티 1번을 조회하기 위해 매니저 em.find(member1)를 호출**

  - 먼저 영속성 컨텍스트 내부에 존재하는지 확인함
  - 영속성 컨텍스트 내부에 아무것도 없으면
    1. 영속성 컨텍스트에서 SELECT 쿼리로 DB 직접 조회 함
    2. 가져온 데이터를 영속성 컨텍스트에 올림(1차 캐시에 저장)
    3. 조회된 데이터를 영속성 컨텍스트에서 반환

**2. 멤버 1번 한 번 더 조회**
  - 영속성 컨텍스트 확인
  - 존재하기 때문에 거기서 바로 객체 반환


#### 1차 캐시
- 한 번 조회한 객체를 영속성 컨텍스트가 내부에 저장해두고 재사용하는 구조
- 영속성 컨텍스트에 이미 등록(캐시)된 객체를 조회할 때는 데이터베이스를 거치지 않아도 됨

#### 동일성 보장
- 트랜잭션 안에서는 같은 엔티티를 여러번 조회해도 영속성 컨텍스트에 보관된 같은 객체를 그대로 반환하므로 항상 동일한 객체임이 보장됨
- 한 번 조회된 엔티티는 트랜잭션 내에서 언제나 동일한 객체로 유지됨


#### 엔티티 수정 예시
**1. 멤버 엔티티 1번을 수정하기 위해 먼저 멤버 엔티티 1번을 조회함 em.find(member1)**

  - member1을 영속성 컨텍스트에 가져옴

**2. 멤버의 이름과 주소를 수정**

**3. 수정 작업이 모두 끝나 트랜잭션이 커밋되면 em.flush()가 실행됨**

  - 이떄 JPA에 있는 영속성 컨텍스트에 등록된 엔티티들을 대상으로 엔티티의 변경 전 상태와 현재 상태를 비교해서 어떤 엔티티가 수정되었는지 찾아냄
  - 값이 달라진 걸 발견하면 변경 내용을 자동으로 UPDATE 쿼리를 생성해서 DB에 전달함
  => 이를 변경 감지라고 함.


#### 변경 감지(Dirty Checking)
- 영속성 컨텍스트가 엔티티의 변경 사항을 자동으로 감지하고, 트랜잭션 커밋 시점에 변경 내용을 DB에 반영하는 것
- 변경 감지는 영속성 컨텍스트가 관리하는 영속 상태의 엔티티에만 적용(영속성 컨텍스트가 관리하지 않는 엔티티는 아무리 바꿔도 JPA가 그 변화를 감지하지 않음)
- 여러 번 수정을 하더라도 트랜잭션이 끝나기 전까지는 SQL이 실행되지 않고, 커밋 시점에 필요한 수정사항만 모아서 한 번에 반영



#### 엔티티 삭제 예시
**1. 멤버 엔티티 1번을 삭제하기 위해 먼저 멤버 엔티티 1번을 조회함 em.find(member1)**

  - member1을 영속성 컨텍스트에 가져옴

**2. 멤버 엔티티 1번을 삭제하기 위해 em.remove(member1)을 호출**

  - 이 메소드가 호출되면 JPA에 있는 해당 엔티티를 삭제 대상으로 표시함
  - 영속성 컨텍스트에서는 더 이상 이 객체를 관리하지 않게 됨
  - JPA가 즉시 delete 쿼리를 실행하지는 않음. 내부적으로 보관해두었다가 트랜잭션의 커밋 시점에 JPA가 내부적으로 .flush()를 자동으로 실행하면서 실제 DELETE 쿼리문이 DB에 전송되며 반영됨


  ### 정리
  - JPA는 엔티티 매니저를 통해 엔티티를 영속성 컨텍스트라는 공간에서 관리함
  - 변경 내용을 즉시 DB에 반영하지 않고 모아두었다가, 트랜잭션이 커밋될 때 필요한 SQL을 한 번에 실행함
  - 엔티티의 변경을 자동으로 감지해 SQL을 생성하고, 데이터베이스와 동기화를 수행함
  - 이미 조회된 엔티티는 영속성 컨텍스트에 저장되어 동일 트랜잭션 내에서 재사용됨

#### .find(): 

JPA가 알아서 해당 데이터를 찾아서 멤버 객체로 변환을 해줌
-> 이건 기본 키를 기준으로 하나의 엔티티만 조회를 할 수 있어서 목록을 조회할 수 없음.

getAllMembers() 같은 상황에는 JPQL 사용해야 함.


#### JPQL
- SQL과 비슷하지만, 테이블이 아니라 엔티티 객체를 기준으로 쿼리 작성
- 즉 데이터베이스의 테이블을 조회하는 게 아니라 멤버 엔티티를 대상으로 쿼리를 작성하는 것

#### em.createQuery()
- JPQL 쿼리를 실행하기 위한 쿼리 객체를 생성
- 쿼리문 내에서 변수 이름 앞에 : 붙이면 파라미터 변수 사용 가능

#### .getResultList()
- JPQL 쿼리가 실제로 실행되고 결과가 리스트 형태로 변환됨
- JPA는 데이터베이스에서 조회한 각 행을 자동으로 멤버 객체로 매핑해서 이 리스트 멤버 형태로 만들어서 서비스 계층에 반환해줌
